# AI-first 重构计划与问题

## 已确认决策

1. 沿用现有 Deno/TS 工程，仅裁剪 CoC；允许数据库和交互 breaking change。
2. 新 TS 库独立设计，旧数据通过离线导入进入新库，不要求运行时复用旧库。
3. 上下文仍按当前回复链选择，不引入群聊事件流，不采集/保存所有普通消息。
4. 传统功能先执行，通过类似 `aiContext("...")` 的显式接口提供事实；AI 看到的内容不必等于 Telegram
   回复文字。
5. 同一消息同时触发传统功能和 AI 时，传统处理完成后再组装上下文并调用 AI。
6. 提及 bot 或回复已识别的 AI 回答触发 AI；仅回复传统 bot 消息不触发，需明确提及等 AI 触发。
7. 非 AI 触发不调用模型、AI 摘要、AI 媒体识别或付费显式缓存。传统
   OCR/下载等原服务正常执行，不属于新增 LLM 调用。

## 消息处理模型

`入站消息 → 传统功能（如匹配）→ 注入事实 → AI 触发检查 → 回复链与事实组装 → 请求快照 → provider → AI 交付`

这是一次消息处理的顺序，不是持久化全群事件总线。

- 传统 handler 不得因已回复 Telegram 而提前跳过后续 AI 判断。
- 没有明确 AI 触发时，到触发检查即结束；不创建 AI Run，不累计模型用量。
- 没有传统功能匹配时，AI 阶段仍可按回复链正常工作。
- AI 触发检查应独立于传统功能的文本匹配，不自动把任意命令、按钮或下载完成事件当作 AI 触发。
- 传统功能产生的多条 Telegram 输出和一次逻辑结果应分开，避免进度消息重复进入上下文。
- 下载等慢任务先完成或进入明确失败/超时状态；不提前启动依赖其结果的 AI，也不先生成一版再自动重生成。

### 注入接口意图（不是最终 API）

```ts
const result = await calculator.calculate(expression);
await interaction.reply(formatForTelegram(result));
interaction.aiContext("计算器结果：表达式 0.1 + 0.2，精确结果 0.3");
// 由外层编排继续判断是否明确触发 AI，而非 handler 直接请求 provider。
```

接口可接受文本或结构化事实，最终签名待实现时确定。应保留 feature、请求/回复消息标识、
chat/topic、执行状态与必要时间，且注入内容应简洁、可追溯。它不是让模型自动选择或执行工具的新功能。

### 上下文组成

- 当前 AI 请求及其选中的回复链/已有 AI 会话历史。
- 本次传统 handler 显式注入的事实。
- 被回复传统 bot 消息的事实是否跨请求保留，见 Q1；不能暗自扩展成普通聊天归档。
- 群/话题隔离、去重、token 预算；只选择相关媒体，不提前下载全部附件。
- 普通消息在成为已触发 AI 请求的选中输入前，不全量记录。实际采用的回复链/事实可保存于 AI 请求快照，
  用于审计、计量和失败重试，不等于收集未触发的群聊历史。
- 用户文本、外部链接内容和传统结果均是上下文数据，不能提升为 system
  指令；密钥、原始内部日志及其他群数据不注入。

### 触发与可靠性

识别“回复 AI 回答”依赖已成功交付的 AI 消息身份，而非 `from.id === bot.id`。 单纯回复
/calc、下载、评分等传统 bot 输出不触发。 已有明确 AI 路由标记（如
@new）的保留方式应记录在新路由设计中；不能用任意 @数字绕过触发检查。

传统执行结果与 AI 生成结果分开计量。AI 请求先落库，生成状态与 token 累计只提交一次；
发送失败保留生成结果，重试不能再次执行已完成的传统下载/计算或重复计量。 Run 应保存所选
provider/model 和实际上下文快照；旧远端会话/cache 状态不能未经验证直接导入并继续使用。

## 新数据库与导入

- 定义 TS 独立 schema/version 和规范查询源；不复制 Go V9/V11 迁移版本链。
- 离线导入器只读旧库、创建新目标，拒绝覆盖已有数据库/媒体。
- 映射用户/群配置、AI 会话/消息/Run/用量/提示词/payload、统计、评分、下载缓存和媒体引用。
- 保留 Telegram chat/message 关联；内部主键可重建，输出 ID 映射。
- 校验条数、token 汇总、assistant/provider 原始 payload、媒体 hash/size、外键与 integrity；
  非一对一映射须逐项解释，不能静默跳过。
- CoC 属性不进入运行时也需独立归档报告，默认不删除。
- 源库及其 migration checksum 不改变；导入失败只影响新建 staging 目标，不发布。
- 迁移不要求保留旧远端链继续可用；原始数据保留，必要时从本地历史重建并标明有损部分。

## 分阶段计划

1. **设计确认**：本文件、功能清单和 AGENTS 已更新；确认 Q1/Q2，定义新 SQL/查询工作流。
2. **新 schema 与导入切片**：临时库回归、迁移映射报告、旧数据保全验收；不在旧库上试写。
3. **请求编排与 aiContext**：传统处理先行、明确触发、请求级注入、reply-chain builder； 先以计算器或
   /roll 的单个传统功能做端到端离线测试。
4. **AI 生命周期/provider**：接入新 repository，保持一次计量、失败保留与 Rich Markdown 交付； 对齐
   Sub2API 和现有多模态能力，不增设自主工具执行。
5. **其余功能迁移**：每个功能分别定义 Telegram 展示与 AI context，迁移统计/下载/B 站/OCR
   等保留能力。
6. **副本导入与切换演练**：验证真实数据副本、备份与回滚；实际停服/上线仍需明确批准。

每个已验收实现切片独立提交并推送。当前 GitHub 远程不可访问；用户显式要求的计划修订可进行，

## 待确认问题

### Q1：传统事实是否跨请求保存？

“包含传统 bot 消息的回复链”存在两种生命周期：

- 仅本次处理：没有触发 AI 时丢弃注入事实；后来回复并提及 bot，只能利用 Telegram 提供的可见回复文字。
- 随传统回复关联保存：只存 handler 显式注入的事实和必要 chat/topic/message 关系； 以后明确触发 AI
  且回复该消息时能取回，仍不保存普通群聊历史。

建议第二种，以保留不同于可见文字的精确事实。请确认是否允许这种传统事实持久化；
如允许，再确定保留时长。确认前不新增背景上下文表，也不沿用此前“普通消息保留七天”的提议。

### Q2：传统功能失败后，明确触发的 AI 是否继续？

建议传统功能正常给出失败提示，注入安全、简洁的失败原因，再继续明确触发的 AI 回复，
使其能解释失败或给出下一步；不注入敏感异常/凭证。不自动重试传统副作用或额外调用模型。
如果希望失败即结束，应改为不进入 AI 阶段。请确认。

## 离线验收用例

- 普通消息：不保存完整消息，不创建 AI Run，不请求 provider。
- 只触发传统功能：执行一次、正常交付；provider/付费缓存调用次数为零。
- 只触发 AI：仅采用回复链/既有 AI 历史及相关事实，不夹带其他群聊消息。
- 同时触发两者：传统处理及事实注入先于 provider；发送给模型的内容可不同于可见回复。
- 回复传统 bot 消息但未提及：不触发 AI；回复 AI 回答：触发；回复传统消息并提及：触发。
- 长任务、失败和交付重试：不重复传统副作用、不重复 token 计量。
- 恶意上下文或跨群/话题引用：不提升为 system 权限，不读取未授权上下文。
